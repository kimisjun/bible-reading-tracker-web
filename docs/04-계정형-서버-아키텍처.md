# 계정형 서버판 아키텍처·동기화·배포 설계

- 상태: 권장 설계안
- 기존판: GitHub Pages 개인 오프라인판 유지
- 확장판: 교인 계정·여러 기기 동기화·관리자 기능을 가진 서버판
- 계정 생성: 개인별 일회용 초대코드 + 직접 가입 + 관리자 대행 발급

## 1. 단계적 운영 전략

현재 동작하고 있는 개인 오프라인판을 즉시 없애지 않는다.

### 1단계 — 현재 개인판 유지

- 로그인 없이 사용
- 브라우저 localStorage 저장
- 기존 사용자 기록 보존
- GitHub Pages 주소 유지

### 2단계 — 계정형 서버판 시범 운영

- 별도 시험 주소에서 운영
- 관리자와 5–10명의 성도가 먼저 시험
- 휴대전화 로그인, 여러 기기 동기화, 오늘·주간 합계 검증
- 실제 60–80대 성도의 가입·비밀번호 복구 사용성 검증

### 3단계 — 교회 전체 확대

- 기존 개인판의 ReadingEvent를 계정으로 가져오는 마이그레이션 제공
- 교회 공식 웹주소로 서버판 배포
- 일정 기간 두 버전을 병행
- 데이터 이전 여부는 성도가 직접 선택

## 2. 권장 기술 구성

### 프런트엔드

- 현재 React + TypeScript + Vite 구조 유지
- 모바일 우선 PWA
- IndexedDB에 오프라인 ReadingEvent와 동기화 대기열 저장
- 서비스 워커로 앱 화면과 정적 자산 캐시
- 성경 본문·오디오는 저장소와 캐시에 넣지 않음

### 관리형 백엔드 권장안

- **Supabase 계열 관리형 PostgreSQL·인증·Edge Function**을 1차 후보로 사용
- PostgreSQL Row Level Security로 성도는 자신의 데이터만 조회
- 관리자 작업과 초대코드 발급은 서버 함수에서만 수행
- 일일·주간 집계는 PostgreSQL 뷰 또는 서버 함수에서 계산
- 관리자 집계는 개인 식별 정보가 제거된 결과만 반환

### 권장 이유

- 별도 서버 운영 부담이 비교적 작음
- PostgreSQL 관계형 모델이 통독 이벤트·계획·감사 로그에 적합
- 인증, 데이터베이스, 백업, 서버 함수를 한 곳에서 관리 가능
- 향후 독립 Spring Boot 서버로 옮기더라도 PostgreSQL 데이터 모델을 재사용 가능

### 대안

- Java 21 Spring Boot + PostgreSQL: 통제력은 높지만 초기 보안·서버·백업 운영 부담이 큼
- Firebase: 실시간 동기화는 편하지만 관계형 통독 계획·집계·감사 로그가 PostgreSQL보다 복잡할 수 있음

최종 공급자 선택 전 휴대전화+비밀번호, 관리자 MFA, 국내 SMS 연동, 비용, 데이터 저장 지역을 실제 설정 환경에서 검증한다.

## 3. 시스템 구조

```text
휴대폰·PC PWA
  ├─ React 화면
  ├─ IndexedDB 로컬 ReadingEvent
  ├─ 동기화 Outbox
  └─ 서비스 워커
           │ HTTPS
           ▼
관리형 인증 + 서버 함수
  ├─ 로그인·세션
  ├─ 초대코드 검증
  ├─ 관리자 권한 검사
  ├─ 요청 횟수 제한
  └─ 집계 API
           │
           ▼
PostgreSQL
  ├─ 사용자·역할
  ├─ ReadingEvent
  ├─ 장별 진행 투영
  ├─ 통독 계획·과제
  ├─ 일일·주간 집계
  ├─ 관리자 동의·감사 로그
  └─ 백업·복구
```

## 4. 가입 흐름

### 성도 직접 가입

1. 관리자가 특정 성도용 일회용 초대코드를 생성한다.
2. 성도는 웹앱에서 초대코드, 이름, 휴대전화 번호, 비밀번호를 입력한다.
3. 서버는 초대코드의 유효기간·사용 여부를 검사한다.
4. 휴대전화 번호를 한국 표준 형식으로 정규화한다.
5. 계정을 생성하고 초대코드를 사용 완료 처리한다.
6. 개인정보 이용 안내와 공유 기본값 비공개를 확인한다.
7. 큰 글자와 알림 시간을 선택한다.
8. 첫 화면으로 이동한다.

### 관리자 대행 발급

1. 관리자가 본인 확인 후 계정을 생성한다.
2. 임시 비밀번호를 발급한다.
3. 성도는 첫 로그인에서 새 비밀번호로 변경한다.
4. 어려운 경우 교회 지정 장소에서 관리자가 변경을 돕는다.

### 초대코드 보안

- 무작위로 충분히 긴 개인별 코드
- 서버에는 원문이 아니라 해시 저장
- 기본 유효기간 7일
- 한 번 사용하면 즉시 폐기
- 반복 실패 횟수 제한
- 관리자 발급·취소 이력을 감사 로그에 기록

## 5. 로그인과 세션

- 로그인 아이디: 정규화한 휴대전화 번호
- 비밀번호 원문 저장 금지
- 관리형 인증 또는 Argon2id 수준의 안전한 비밀번호 해시 사용
- 로그인 실패 횟수 제한
- 세션 만료와 안전한 갱신
- 관리자 계정은 TOTP 등 다중 인증 필수
- 공용 PC에서 `로그인 상태 유지`는 기본 해제
- 모든 통신 HTTPS

### 비밀번호 분실

초기 운영:

- 교회 관리자에게 본인 확인 후 임시 비밀번호 발급 요청
- 기존 세션 전체 로그아웃
- 첫 로그인에서 비밀번호 변경 강제

추후:

- 정식 국내 SMS 공급자를 연결한 본인 인증 재설정 추가
- SMS 비용과 발송 실패·번호 변경 절차를 별도로 운영

## 6. ReadingEvent 원장

통독 합계가 아니라 ReadingEvent를 원본으로 저장한다.

```text
ReadingEvent
- id: UUID
- userId
- deviceId
- bookId
- chapterNumber
- action: READ | CANCEL
- source: DAILY_PLAN | FREE_READING | REREAD | IMPORT
- planAssignmentId: 선택
- groupId: 묶음 완료 시 선택
- occurredAt: 기기에서 기록한 시각
- receivedAt: 서버가 받은 시각
- timezone: Asia/Seoul
- targetEventId: 취소 시 원본 이벤트
- idempotencyKey
```

### 원칙

- 이벤트를 물리 삭제하지 않고 CANCEL 이벤트로 취소
- UUID와 idempotencyKey로 재전송 중복 방지
- 같은 계획 과제의 같은 장을 반복 눌러도 한 번만 인정
- 실제 다시 읽은 경우에만 REREAD 이벤트 생성
- 전체 고유 장 진도와 일일·주간 읽은 장 수를 이벤트에서 다시 계산 가능

## 7. 오늘·주간 통독량 집계

### 오늘 통독량

- 한국 시간 오늘 00:00–23:59의 유효 READ 이벤트 합계
- 취소된 이벤트 제외
- 계획, 자유 통독, 다시 읽기를 나누어 표시

### 주간 통독량

- 한국 시간 월요일 00:00–일요일 23:59
- 월–일 각 날짜의 유효 READ 이벤트 수
- 이번 주 총합은 7일 합계
- 서버 집계를 최종값으로 사용하고, 오프라인 중에는 로컬 예상값을 `동기화 대기`와 함께 표시

### 전체 진도

- 유효 READ 이벤트가 한 번 이상 존재하는 고유 `(bookId, chapterNumber)` 수
- 반복 읽기는 전체 1,189장 진행률을 100% 이상으로 만들지 않음

## 8. 오프라인과 여러 기기 동기화

### 오프라인 기록

1. 사용자가 장을 누르면 IndexedDB에 즉시 ReadingEvent 저장
2. 화면에 바로 반영
3. Outbox에 동기화 대기 등록
4. 인터넷이 연결되면 서버에 순서대로 전송
5. 서버가 UUID와 idempotencyKey로 중복 확인
6. 성공 시 동기화 완료 표시

### 화면 상태

- `저장됨`: 서버까지 반영
- `동기화 대기`: 기기에 안전하게 저장됐으나 서버 전송 전
- `확인 필요`: 계정 만료·충돌·검증 오류

### 충돌 정책

- 읽기 이벤트는 합치되 중복 이벤트는 제거
- 취소는 targetEventId를 기준으로 반영
- 묵상 메모는 양쪽 사본을 보존하고 사용자에게 선택 요청
- 연속일·오늘·주간 합계는 서버에서 이벤트를 다시 계산
- 기기 시간이 크게 잘못된 경우 receivedAt과 비교해 확인 요청

## 10. 개인정보 보호

- 관리자 기본 API에는 개인 상세 기록을 반환하지 않음
- 전체 통계는 최소 인원 기준을 적용해 소수 집단의 개인 추정 방지
- 개인 기록 열람은 성도 동의 토큰과 만료 시각이 있어야 함
- 관리자 열람·내보내기·수정은 모두 감사 로그 기록
- 성도는 열람 이력과 현재 동의 상태를 확인하고 철회 가능
- 휴대전화 번호는 표시용 암호화 값과 검색용 안전한 식별값을 분리하는 방안 검토
- 개인정보 보유 기간과 탈퇴 후 삭제 일정을 운영정책에 명시

## 11. 백업·복구

### 서버

- PostgreSQL 자동 백업과 시점 복구 지원 여부 확인
- 정기 복구 훈련
- 백업 접근 권한 최소화
- 감사 로그는 일반 통독 데이터보다 긴 보존 기간을 별도 검토

### 성도

- 본인 ReadingEvent·계획·설정을 JSON으로 내보내기
- 기존 개인판 JSON을 계정으로 가져오기 전 미리보기
- 중복 이벤트를 검사한 뒤 병합
- 가져오기 전 서버 스냅샷 생성
- 적용 결과와 제외된 기록을 사용자에게 안내

## 12. 배포 권장안

### 기존 개인판

- 현재 GitHub Pages 주소 유지
- 로그인 없는 오프라인판으로 안내

### 계정형 서버판

- 교회 공식 하위 도메인 사용 예: `bible.asanjeil.org`
- PWA 프런트엔드는 관리형 정적 호스팅
- 인증·DB·서버 함수는 별도 관리형 백엔드
- 개발·시험·운영 환경 분리
- 운영 배포 전 관리자 MFA, 백업 복구, 접근 로그 검증

GitHub Pages만으로는 비밀 키·관리자 서버 로직·데이터베이스를 안전하게 운영할 수 없으므로 계정형 서버판 전체를 GitHub Pages에만 두지 않는다.
